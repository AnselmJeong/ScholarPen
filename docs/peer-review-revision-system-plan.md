# ScholarPen 가상 심사·실제 Peer Review 대응 시스템 설계서

- 작성일: 2026-10-25
- 상태: 구현 전 상세 계획. 이 문서 작성으로 앱 기능이나 실제 원고가 변경되지는 않는다.
- 코드 확인 기준: ScholarPen 1.7.0, Git `69bc3c3`
- 목표: GPT의 검토와 Claude의 통합 수정·답변을 연결하되, 원본을 보존하고 여러 심사자의 요구가 원고 전체의 논리를 훼손하지 않게 한다.
- 기본 결정: 가상 심사와 실제 심사 대응에 하나의 세션 엔진을 사용한다. Claude의 실질적 수정은 세션당 최대 2회이며, 각 수정 뒤 GPT가 원고와 답변을 함께 검토한다.

## 1. 제품 목표와 성공 기준

이 기능의 단위는 채팅이나 개별 코멘트가 아니라 **원고·표·그림·참고문헌·심사의견·답변을 함께 관리하는 심사 대응 세션**이다. 여러 코멘트를 순서대로 반영하는 방식은 같은 문장을 반복 수정하거나 서로 다른 결론을 만들 수 있다. 따라서 모든 의견을 먼저 검토하고 하나의 수정계획을 세운 뒤, 그 계획을 원고 전체에 적용한다.

사용자는 다음 결과를 얻는다.

1. 실행 당시 원본 원고와 관련 자료의 고정된 사본.
2. 심사자별 의견과 처리 근거가 연결된 목록.
3. 최대 두 차례의 통합 수정을 거친 별도 원고.
4. 실제 반영된 변경에 근거한 point-by-point response.
5. 원본 대비 변경표, 표·그림 검증 결과, 미해결 사항.
6. 수정본과 답변서를 다시 열고 검토·편집·내보낼 수 있는 작업 공간.

성공은 “모든 코멘트를 닫았다”가 아니다. 부당하거나 근거가 부족한 요구에는 반박하거나 판단을 보류하면서도, 원고와 답변의 일관성이 유지되어야 한다. GPT의 최종 판정은 내부 점검 결과이며 실제 게재 가능성이나 심사자 동의를 보장하는 판정으로 표시하지 않는다.

### 1.1 반드시 지킬 요구사항

| 요구 | 설계상 보장 |
|---|---|
| GPT가 검토하고 Claude가 수정·답변 | 역할별 provider/model을 세션에 고정하고 호출마다 명시 |
| 최대 두 번의 cycle | 백엔드 상태 전이에서 수정 회수 상한 2 강제 |
| 원본과 수정본 분리 | 별도 폴더·저장 루트·협업 세션·참고문헌·검색 범위 |
| 실제 심사에도 동일한 절차 | 첫 리뷰의 입력만 사람의 의견으로 교체 |
| 다수 reviewer 대응 | 의견별 식별자와 reviewer 정체성 보존, 충돌을 통합 계획에서 해결 |
| 전체 흐름 보존 | 논증 지도, 보호할 연구 사실, 변경 영향 관계, 최종 전체 검토 |
| 표 자동 수정 | 별도 작업본에 구조화된 패치 적용, 수치는 근거·재현 가능한 계산으로 검증 |
| 그림 재작성은 승인 필요 | 이미지·벡터·도표 재생성 전에 그림별 승인, 미승인 실행 차단 |
| 수정과 답변 일치 | 답변을 실제 반영된 변경과 연결하고 GPT가 재검증 |
| 중단 후 복구 | 단계별 영속 저장, 부분 출력을 완성본으로 승격하지 않음 |

## 2. 현재 앱에서 재사용할 기반과 부족한 부분

아래는 계획서 작성 시 코드를 읽어 확인한 사항이다. 계정 연결 상태나 설치된 앱의 실제 동작을 이번 작업에서 재시험한 것은 아니다.

| 영역 | 현재 기반 | 이번 기능에서 추가할 것 |
|---|---|---|
| 모델 연결 | `src/bun/agent/providers.ts`의 공통 호출이 `codex`와 `anthropic`을 각각 구독 클라이언트로 전달 | reviewer와 reviser를 동시에 별도 설정; 사이드바의 단일 선택과 분리 |
| GPT 구독 | `src/bun/codex/client.ts`의 모델 조회, 인증·한도 확인, 이미지 입력, 도구 없는 일시적 turn | 세션 입력 묶음, 모델 고정, 단계별 provenance |
| Claude 구독 | `src/bun/claude/client.ts`의 구독 CLI 경로와 이미지 입력 | 통합 계획·구조화된 수정·답변 단계의 역할 어댑터 |
| 자동 리뷰 | `src/bun/collab/agent/reviewer.ts`의 문단 검토·분류·근거 위치 | 원고 전체 및 표·그림을 포함한 명시적 심사 세션 |
| 통합 수정 | `src/bun/collab/agent/bulk-comments.ts`의 모든 의견을 함께 읽는 규칙, 보호된 텍스트 수정, 충돌 검출, 임시 문서 검증 | 여러 파일과 표 구조를 포함한 세션 단위 계획·패치; 수정 없이 반박하는 결과 |
| 답변서 | `src/shared/collab/revision-log.ts`와 `RevisionHistory.tsx`의 변경 이력·Markdown 답변 생성 | reviewer/round별 원문 보존, 전체 길이의 답변, 최종 패키지와의 증거 연결 |
| 일관성 | `project-consistency.ts`의 참조·용어·중복·모순 검사와 `manuscript-map.ts` | 표·그림·수치 관계 및 논증 흐름 검사, 회차별 비교 |
| 문서 저장 | 프로젝트의 `documents/`, 협업 Y.Doc, 히스토리 | 원본·작업본·회차별 결과를 분리하는 저장 범위 |
| 표·그림 | BlockNote/Quarto 표, 프로젝트 상대경로 그림, 캡션·참조 식별자 | 표의 셀·열·주석 패치 및 실제 이미지 검토, 승인된 그림 교체 |
| 장시간 작업 | `src/bun/collab/project-jobs.ts`의 메모리 기반 작업 상태 | 앱 재시작 후에도 복구 가능한 상태 머신과 작업 기록 |

### 2.1 기존 기능을 그대로 이어 붙이면 생기는 문제

- 기존 통합 수정은 열려 있는 단일 문서의 편집 가능한 텍스트 구간을 중심으로 동작한다. 다른 원고는 읽기 문맥이며 표 구조 수정과 여러 문서의 동시 반영을 완전히 해결하지 않는다.
- 기존 `addressed` 판정은 실제 변경 문단을 요구한다. “원문을 유지하는 정당한 반박”과 “이미 설명되어 있어 위치만 안내”를 새 결과 유형으로 지원해야 한다.
- 기존 revision log는 본문·의견·답변을 항목당 2,000자로 자른다. 심사의견 원문이나 공식 답변의 원장으로 사용하면 안 된다.
- manuscript map은 긴 문서를 발췌하고 항목 수를 제한한다. 요약 지도만으로 전체 원고를 읽었다고 판정하면 안 된다.
- 일반 문서 문맥은 그림 경로나 캡션을 포함할 수 있지만, 그것만으로 이미지 픽셀이 모델에 전달되지는 않는다.
- 현재 이미지 검증은 메시지당 최대 4개, 이미지당 5 MB이다. 그림 수가 많은 원고는 명시적인 배치와 검토 범위 기록이 필요하다.
- 프로젝트 참조 인덱스, 메모리, 다른 문서 검색이 원본과 수정본을 함께 읽으면 과거 내용이 새 원고의 사실처럼 섞일 수 있다.
- 기존 자동 reviewer와 새 세션 엔진이 동시에 작업본을 수정하면 예측할 수 없는 추가 반복이 생긴다. 세션 작업본에서는 기존 자동 수정·자동 리뷰를 기본 중지한다.

## 3. 두 가지 모드와 정확한 반복 규칙

### 3.1 가상 심사

```text
원본 고정 + 자료 검사
  → GPT 초기 심사 C0: reviewer별 독립 의견 생성
  → Claude 통합 계획 + 1차 수정 M1 + 답변 S1
  → 규칙 기반 검사 + GPT 재검토 V1
      ├─ 충분히 해결됨 → M1/S1을 최종 후보로 선택
      └─ 수정 가능한 문제가 남음
          → Claude 통합 계획 갱신 + 2차 수정 M2 + 답변 S2
          → 규칙 기반 검사 + GPT 최종 검토 V2
          → 최종 후보 + 남은 이슈 확정, 자동 수정 종료
```

**한 cycle은 Claude의 한 차례 실질적 통합 수정·답변과 그 뒤의 GPT 재검토를 뜻한다.** 초기 GPT 심사 C0는 cycle에 포함하지 않는다. 2회 실행 시 GPT의 논리적 검토 단계는 초기 심사·1차 재검토·최종 검토의 총 3단계다. reviewer별 호출, 긴 문서 분할, 표·그림 검사 등으로 실제 모델 호출 수는 더 많을 수 있다.

기본 reviewer는 3개 역할로 제안한다: 분야·기여도, 방법·통계, 논리·보고 완결성. 사용자는 시작 화면에서 수와 관점을 바꿀 수 있다. 역할별 초기 심사는 서로의 의견을 보지 않고 수행하며, 이후 중복 의견을 묶되 출처 reviewer는 유지한다. 같은 GPT가 역할을 나누는 것이므로 서로 독립적인 실제 전문가 3명을 대체한다고 설명하지 않는다.

### 3.2 실제 Peer Review 대응

```text
실제 제출본 고정 + 편집자 결정문/Reviewer 1..N 의견 입력
  → 원문 보존 + 의견 분해·위치 연결
  → Claude 통합 계획 + 1차 수정 M1 + 실제 심사자용 답변 S1
  → 규칙 기반 검사 + GPT 내부 재검토 V1
  → 필요하면 Claude 2차 수정 M2 + 답변 S2
  → 규칙 기반 검사 + GPT 내부 최종 검토 V2
  → 재투고 후보 패키지, 자동 수정 종료
```

첫 리뷰 입력은 실제 사람의 의견이다. GPT가 이를 새 가상 심사로 대체하거나 원문 의미를 바꾸면 안 된다. GPT는 이후 “각 요구에 정확히 답했는가, 수정 때문에 새로운 문제가 생겼는가”를 점검한다. 내부 GPT 지적은 실제 reviewer의 발언처럼 답변서에 인용하지 않는다.

실제 심사가 검토한 제출본을 기본 baseline으로 삼는다. 사용자가 그 이후 수정한 초고를 사용하면 제출본과 현재본을 별도 입력으로 기록하고 차이를 표시한다. 제출본이 없으면 위치 매칭에 한계가 있음을 기록하고, 존재하지 않는 원본 페이지·행 번호를 만들지 않는다.

### 3.3 중단·조기 종료·추가 작업 규칙

- 상한은 2, 기본값도 2이며 사용자는 1회만 실행할 수 있다.
- V1에서 추가 실질 수정이 필요 없으면 조기 종료한다. 무조건 두 번 다시 쓰지 않는다.
- 두 번째 수정 후 V2는 판정과 미해결 목록만 만든다. 숨겨진 3차 수정, 자동 재시작, 품질 점수 상승을 위한 반복을 금지한다.
- 미해결 사실·연구 설계 선택·승인되지 않은 그림은 이유를 남긴다. “검토 완료”와 “제출 준비 완료”를 구분한다.
- V2가 M2의 심각한 퇴행을 발견하면 M1과 비교해 일관된 기존 패키지를 최종 후보로 선택할 수 있다. M2 원고에 S1 답변을 붙이는 식의 혼합은 금지한다.
- 네트워크 재시도나 JSON 형식 복구는 같은 단계의 기술적 재시도다. 새로운 논증·수정은 다음 cycle로만 처리한다. 같은 단계 재시도는 최대 2회로 제한하고 기록한다.
- 부분 변경을 적용한 뒤 실패한 경우 롤백하거나 완료된 동일 결과를 복구한다. 다른 내용을 다시 생성해 같은 cycle에 무제한 반영하지 않는다.
- 두 회차가 끝난 뒤 더 고치려면 사용자가 수동 편집하거나 후속 세션을 시작한다. 후속 세션은 부모 세션과 baseline을 명시한다.

후속 GPT 검토는 최초 심사 기준과 실제 reviewer의 요구를 유지한다. 이미 해결된 의견은 변경으로 문제가 재발했거나 새로운 근거가 생긴 경우에만 다시 연다. 새 의견에는 `previous-comment-followup`, `revision-regression`, `new-critical-issue` 같은 출처를 기록한다. 개인적 문체 취향이나 계속 달라지는 평가 기준으로 수정 목표를 늘리지 않는다.

## 4. 역할 분담과 모델 호출 원칙

| 역할 | 담당 | 입력 | 출력 |
|---|---|---|---|
| 자료 수집·범위 확정 | 앱 | 선택한 원고, 연결 자료, 저장 상태 | 고정된 입력 목록과 해시 |
| 초기 가상 심사 | GPT / `codex` | 원고 전체, 표, 그림, 출처, 저널 기준 | 심사자별 의견·근거 위치·중요도 |
| 실제 의견 구조화 | 앱 + 필요시 GPT | 사람의 원문과 제출본 | 원문에 연결된 개별 의견, 불확실한 매칭 |
| 의견 조정·통합 수정 | Claude / `anthropic` | 전체 의견, 전체 원고, 연구 사실, 이전 결정 | 통합 계획, 구조화된 변경안, 보류·반박 근거 |
| 적용·정합성 검사 | 앱 | 변경안, 기준 버전 | 검증된 작업본과 실제 변경 기록 |
| 답변 작성 | Claude | 실제 적용 결과, 원문 의견, 위치 정보 | reviewer별 답변 및 변경 근거 |
| 재검토·최종 판정 | GPT | 원본 대비 차이, 현재 전체 원고, 모든 답변, 표·그림 | 해결 여부, 반박 타당성, 새 모순, 남은 문제 |
| 그림 실행 승인 | 사용자 | 수정 필요성, 입력 자료, 변경 계획, 자원 예상 | 승인·거절·보류 |

호출 원칙:

1. 역할 설정을 세션 생성 시 저장한다. 일반 채팅의 provider를 바꾸어도 실행 중 세션은 바뀌지 않는다.
2. “GPT” 선택은 현재 Codex 구독 연결에서 제공되는 모델 목록을 사용한다. ChatGPT 웹의 모든 모델을 선택할 수 있다고 가정하지 않는다. Claude도 현재 구독 클라이언트가 지원하는 선택을 사용한다.
3. 기존 구독 어댑터와 인증·한도 검사를 재사용한다. 별도 API key 경로나 유료 API 자동 fallback을 만들지 않는다.
4. 구독 연결이 무제한 실행을 뜻하지 않는다. 한도·인증·모델 접근 오류에서는 해당 단계에서 멈추고 저장된 결과를 유지한다. Claude의 계정별 추가 사용 가능성은 기존 연결 정책을 따르며 앱이 절대적인 무과금 보장을 새로 주장하지 않는다.
5. 모델은 파일을 직접 수정하지 않는다. 모델은 구조화된 제안만 반환하고, 앱이 세션의 허용된 파일에 검증된 변경을 적용한다.
6. provider/model/CLI 버전/프롬프트 버전/입력 해시/실제 반환 모델 정보(있는 경우)를 기록한다. 대화의 숨은 상태에 의존하지 않는다.
7. 필요한 문헌 확인은 기존 검색·인용 도구를 명시적으로 호출한다. 새 문헌은 DOI·서지정보와 확인한 범위를 저장하며, 초록만 읽고 전문을 검증했다고 주장하지 않는다.
8. 모델의 JSON/schema 준수를 가정하지 않는다. 파싱·스키마·식별자·근거 검사를 모두 통과한 결과만 다음 단계로 넘긴다.

## 5. 폴더 분리와 원본 보존

### 5.1 권장 저장 구조

기존 프로젝트 안에 별도 `reviews/` 루트를 둔다. 이 폴더는 일반 원고·draft 검색에서 제외하고 전용 화면으로 접근한다. 아래 `project/`는 각 버전이 자신의 `documents/`, `figures/`, `resources/`, `exports/references.bib`를 갖는 독립적인 문서 묶음을 의미한다.

├── figures/
├── resources/
├── exports/references.bib             # 기존 프로젝트의 canonical bibliography
└── reviews/
    └── 2026-10-25-virtual-<session-id>/

        ├── manifest.json              # 입력 파일, 원래 위치, 해시, 읽기 범위
        ├── original/                  # 실행 당시 baseline, 읽기 전용
        │   └── project/
        │       ├── documents/
        │       ├── figures/
        │       ├── resources/
        │       └── exports/references.bib
        ├── inputs/
        │   ├── decision-letter.txt
        │   ├── reviewer-01-original.txt

### 5.2 스냅샷 생성 절차

1. 선택한 manuscript set과 관련 자료를 확정한다. 프로젝트의 모든 초고를 무조건 포함하지 않는다.
2. 열린 편집기의 저장되지 않은 변경과 Y.Doc를 저장하고 완료 응답을 기다린다. 저장 시점과 파일 복사 시점 사이에 내용이 바뀌면 다시 스냅샷을 잡는다.
3. 미결정 tracked change가 있으면 자동 수락하지 않는다. 원래 제안 상태를 보존하고, 사용자가 검토할 기준 본문을 정하도록 시작 전 항목으로 표시한다. 결정 전에는 provider 호출을 시작하지 않는다.
4. 원고, 표, 연결 그림, 실제 사용되는 참고문헌 파일, 필요한 보충자료·데이터·설정·확장 파일을 의존 관계에 따라 복사한다. 인증 설정·개인 토큰은 복사하지 않는다.
5. 파일별 SHA-256과 전체 입력 해시를 만든다. 원본 JSON 바이트는 보존한다. 작업본에 필요한 경로 정규화는 별도 사본에서만 한다.
6. 외부 절대경로, symlink, 원격 이미지 등을 발견하면 실제 내용을 세션에 동결하거나 `unavailable`로 기록한다. 원본의 링크 문자열을 보존하되 뷰어는 고정된 경로 매핑을 사용한다. 현재 원본 파일로 조용히 되돌아가 읽지 않는다.
7. `original/` 고정 후 `workspace/project/`를 별도 복사하고, 작업본의 파일 참조는 작업본 내부로 연결한다. 파일이 빠지거나 경로가 탈출하면 실행을 중지한다.
8. 원본과 각 회차 결과는 앱 수준의 쓰기 금지 대상으로 등록한다. OS 읽기 전용 속성은 추가 보호일 뿐 유일한 보호 장치로 삼지 않는다.

하드링크와 수정 가능한 symlink로 사본을 만들지 않는다. 파일 사본 또는 쓰기 분리가 보장된 copy-on-write 복사를 사용한다. 임시 폴더와 최종 폴더는 같은 볼륨에 두어 rename 기반 확정이 가능하게 한다.

### 5.3 저장 경계의 실제 구현 원칙

- 모든 저장·자동 저장·협업 RPC는 `sessionId`, `workspaceId`, 문서 ID를 통해 허용된 루트를 조회한다. 클라이언트가 임의 경로를 써 넣지 못하게 한다.
- 기존 저장 함수는 `projectPath/documents/`와 `.scholarpen/`를 전제로 한다. 작업본을 등록된 독립 루트로 연결하는 어댑터를 추가한다. 전역 경로 검사를 느슨하게 만들어 해결하지 않는다.
- `original/`, `rounds/`, `final/`은 읽기 전용 뷰어로 열고 자동 저장 가능한 일반 editor 세션에 연결하지 않는다.
- BlockNote block ID는 대응 관계를 위해 유지하되, 문서·Y.Doc 식별 키에 workspace 구분을 포함한다. 원본의 협업 큐·awareness·자동 reviewer 실행 상태를 복제하지 않는다.
- 각 작업본의 canonical bibliography는 그 작업본 안의 `exports/references.bib`다. 원 프로젝트의 서지 파일을 갱신하지 않는다.
- 참조 인덱스·문헌 검색·manuscript map·프로젝트 메모리·Hindsight에 scope를 전달한다. 리뷰 결과가 원 프로젝트의 장기 기억으로 자동 유입되지 않게 한다. 범위를 구분할 수 없는 메모리 경로는 세션에서 사용하지 않는다.
- 같은 논문의 서로 다른 회차를 “다른 장의 원고”로 읽거나 중복 경고 대상으로 삼지 않는다. 회차 비교는 명시적인 비교 입력으로만 제공한다.
- 원 프로젝트가 이후 바뀌어도 진행 중 세션의 baseline은 변하지 않는다. 최신 원고 반영은 새 baseline/세션으로 처리한다.
- 원본으로 자동 덮어쓰기하는 “적용” 동작은 만들지 않는다. 최종본은 별도 폴더에서 계속 쓰거나 새 프로젝트로 복사해 연다.

## 6. 원고 전체의 일관성을 지키는 방법

### 6.1 논문 기준표: Manuscript Contract

리뷰 전에 원고에서 다음 항목을 추출해 출처 위치와 함께 고정한다.

| 항목 | 내용 |
|---|---|
| 핵심 질문·목적 | 어떤 문제를 다루며 무엇을 범위 밖에 두는가 |
| 주요 주장 | 주장, 근거 위치, 확실성 수준, 적용 범위 |
| 연구 설계·자료 | 설계, 모집단, 표본 수, 분석 대상, 측정·분석 방법 |
| 핵심 결과 | 수치, 단위, 통계량, 조건·시점·하위집단 |
| 용어·정의 | 약어, 변수, 개념의 정의와 허용 표현 |
| 논증 구조 | 각 절이 전체 논증에서 맡는 역할, 앞뒤 의존 관계 |
| 제한·저자 결정 | 기존 한계, 유지할 관점, 저자가 명시한 금지·허용 사항 |

이 기준표는 원고의 오류까지 보호하는 장치가 아니다. 기존 사실의 오류가 확인되면 출처와 수정 근거를 남기고 갱신할 수 있다. 다만 reviewer의 취향이나 AI의 추측만으로 연구 설계, 실제 결과, 핵심 입장을 바꿀 수 없다. 자동 추출이 불확실한 항목은 확정 사실과 구분하며 필요할 때만 저자에게 묻는다.

### 6.2 의견 등록과 충돌 조정

1. 모든 의견에 안정적인 ID를 부여한다. 예: `R1-C03`, `R2-C07`, `ED-C02`. 여러 요구가 섞인 한 의견은 하위 항목으로 분해하되 원문·순서·부모 의견을 유지한다.
2. 각 의견을 주제, 중요도, 근거, 대상 블록/표/그림, 필요한 작업, 예상 영향 범위로 분류한다.
3. 같은 요구는 하나의 수정 작업으로 묶는다. 그래도 각 reviewer에게 별도 답변을 남긴다.
4. 충돌 관계를 표시한다: 상반된 주장, 같은 구간의 다른 수정, 선행 작업 필요, 데이터 요구, 그림 승인 필요.
5. 우선순위는 **확인된 근거와 연구 사실 → 저자의 명시적 결정 → 편집자·저널의 필수 조건 → 심사자의 요청 → 문체 선호**로 둔다. 필수 조건이라도 실제 자료와 모순되면 수행했다고 꾸미지 않는다.
6. Claude가 전체 원고에 적용할 하나의 통합 계획을 만든다. 표·그림·초록·결론까지 포함한 영향을 명시한다.
7. 서로 양립할 수 없는 핵심 선택만 저자 판단으로 남긴다. 명확한 오탈자, 참조 오류, 일관된 용어 정리는 자동 처리한다.

예시: R1이 인과적 결론을 더 강하게 쓰라고 하고 R2가 관찰연구의 한계를 지적한 경우, 두 요구를 각각 반영해 본문과 결론을 모순되게 만들지 않는다. 연구 설계가 허용하는 연관성 수준을 유지하고, 설명을 보강하되 R1에는 인과 표현을 확대하지 않은 이유를 답한다.

### 6.3 변경 영향 관계와 수정 후 검사

주장·수치·용어·표·그림을 근거 관계로 연결한다. 예를 들어 Results의 효과크기 표현을 수정하면 같은 결과를 인용하는 Abstract, Discussion, Conclusion, 표 주석, 그림 캡션, response 항목을 함께 점검한다.

검사는 세 층으로 나눈다.

- **구조 검사:** 손상된 블록, 사라진 인용, 깨진 식별자, 누락된 파일, 중복 label, 표 열 수 불일치 등을 코드로 검사한다.
- **근거 검사:** 수치·단위·표본·조건이 자료와 맞는지, 답변의 “변경했다”는 주장이 실제 차이와 연결되는지 확인한다.
- **논증 검사:** 전제→분석→해석→결론의 연결, 과도한 단정, 중복·단절, reviewer별 수정의 충돌을 GPT가 전체 맥락에서 검토한다.

단순 문자열 비교로 서로 다른 하위집단의 표본 수를 오류로 판단하지 않는다. 수치에는 집단·조건·분모·시점·단위·출처를 함께 저장한다. 충돌 해소는 어느 숫자가 더 자주 등장하는지로 결정하지 않는다.

### 6.4 긴 원고와 여러 문서

- 사용자가 정한 문서 순서와 포함 범위를 `manuscriptSet`으로 저장한다. 주 원고, 보충자료, 참조 전용 문서를 구분한다.
- 입력이 충분히 작으면 전체 원고와 자료를 함께 전달한다. 한도를 넘으면 절별 검토와 전체 논증 통합 검토를 단계적으로 수행한다.
- 모든 절을 빠짐없이 읽고, 각 절에는 전체 논증 지도·관련 수치·해당 reviewer 의견·전후 절 문맥을 제공한다. 원문 접근을 요약만으로 대체하지 않는다.
- 수정 전에 전체 의견과 전체 원고의 읽기 단계를 끝낸다. 여러 구간의 패치를 따로 만들더라도 하나의 전역 계획과 같은 candidate에 모아 검사한 뒤 한 번에 확정한다.
- `coverage.json`은 각 단계가 읽은 문서/절/표/그림/응답과 해시, 누락·발췌 여부를 기록한다. 빠진 부분이 있으면 전체 검토 완료로 표시하지 않는다.
- 토큰 예산은 텍스트뿐 아니라 표·이미지·모델 출력 여유를 포함한다. 기존의 문자 수 상한을 토큰 상한으로 오인하지 않는다.

## 7. 표 검토와 자동 수정

표는 텍스트처럼 다시 생성하지 않고 구조화된 개체로 다룬다. 표 ID, 행·열 ID, 헤더, 셀 원문, 단위, 캡션, 각주, 인용, 데이터 출처, 계산식을 추출한다. 기존 표에는 안정적인 행·열 식별자가 없을 수 있으므로 세션에서 대응 ID를 만든다.

### 7.1 검토 항목

- 연구 질문과 Results 설명에 필요한 표인가; 본문과 과도하게 중복되는가.
- 표 제목·열 이름·집단·표본 수·측정 단위·약어·각주가 명확한가.
- 본문의 수치와 표의 값이 같은 분석·분모·시점에 해당하며 일치하는가.
- 합계·백분율·반올림·결측값 표기가 일관되는가.
- 검정법·효과크기·불확실성 표기가 실제 자료와 맞는가.
- 표를 재배열하거나 나눌 때 본문 참조와 논리 순서가 유지되는가.

### 7.2 자동 변경 범위

| 변경 | 처리 |
|---|---|
| 헤더·캡션·약어·단위 표기 정리 | 의미와 근거를 유지하는 범위에서 자동 적용 |
| 행·열 순서 변경, 표 분리·병합 | 데이터·각주·인용을 보존하고 모든 참조를 갱신할 수 있을 때 자동 적용 |
| 숫자 표시 자릿수·백분율 표시 | 원시 정밀도와 계산 규칙을 보존하며 자동 정리 |
| 합계·백분율 등 재계산 | 명시된 입력과 확정된 분모·계산식이 있을 때 앱의 계산기로 수행 |
| 원자료와 명백히 다른 셀 교정 | 신뢰 가능한 출처가 정해져 있고 재현 가능한 경우 자동 교정 |
| 근거 없는 숫자 교체·누락값 추측 | 금지; 자료 요청 또는 미해결 처리 |
| 통계 방법·분석 대상 변경 | 단순 표 수정 범위를 넘는다. 저자 판단과 필요한 분석 결과를 기다림 |
| 의미 있는 결과의 삭제·새 결과 추가 | 근거와 기존 저자 결정으로 정당화할 수 없으면 자동 실행하지 않음 |

표 수정에는 별도의 일괄 승인 절차를 요구하지 않는다. 다만 자동화 권한이 연구 결과를 만들어낼 권한은 아니다. 원자료가 없으면 가능한 표현·구조 정리까지만 수행하고 수치 문제는 열린 상태로 둔다.

### 7.3 적용 방식

- Claude는 `set-cell`, `rename-header`, `reorder-rows`, `update-caption` 등 허용된 작업으로 패치를 제안한다. 임의 파일 덮어쓰기는 허용하지 않는다.
- 각 패치에 기준 표 해시, 이전 값, 새 값, 근거, 관련 comment ID를 붙인다.
- 앱이 기준 해시와 이전 값 일치를 확인한 뒤 작업본에 적용한다. 계산은 앱이 검증 가능한 연산으로 실행하며 모델이 임의 생성한 코드를 자동 실행하지 않는다.
- 셀 값의 근거와 표시값을 분리하여 반올림된 값으로 다시 통계를 계산하지 않는다.
- 표 변경은 본문·캡션·참고문헌 변경과 하나의 candidate transaction으로 검증한다. 표만 바뀌고 본문은 실패한 상태를 회차 완료로 저장하지 않는다.
- 모든 변경은 셀 단위 전후 비교로 제공하고 기존 JSON·Quarto 표현으로 저장/재열기/내보내기 가능한지 검증한다.
- 이미지로만 제공된 표는 OCR 추출값을 원자료로 간주하지 않는다. 검증된 셀 값만 구조화하며, 불확실한 수치의 자동 교체는 보류한다.

## 8. 그림 검토와 재작성 승인

### 8.1 반드시 함께 읽을 자료

각 그림은 실제 이미지, 그림 ID, 캡션, 본문 호출 구간, 대응 표·데이터, 가능한 경우 생성 스크립트를 묶는다. 이미지가 여러 패널이면 패널별 표기와 본문의 지칭도 확인한다.

검토는 연구 질문과의 관련성, 축·단위·범례·오차막대·집단 표기, 캡션의 정확성, 본문 해석과의 일치, 가독성, 핵심 정보를 전달하는 데 적절한 형식을 포함한다. 픽셀만으로 정밀한 통계값을 확정하거나 그래프를 보고 원자료를 재구성하지 않는다.

이미지는 지원되는 포맷과 용량으로 읽기 전용 preview를 만들고 배치별로 전달한다. PDF/SVG의 표시용 래스터화나 축소는 검토를 위한 변환이며 출판용 그림 재작성으로 취급하지 않는다. 단, 변환으로 작은 글자가 사라지면 고해상도·패널별 추가 검토를 수행하고 미확인 영역을 기록한다.

### 8.2 자동 처리와 승인 경계

| 작업 | 정책 |
|---|---|
| 캡션의 오탈자·설명 명확화, 본문 참조 정리 | 새 사실을 만들지 않는 범위에서 자동 수정 |
| 번호·교차참조 갱신 | 안정적인 figure ID를 유지하며 자동 처리 |
| 그림 자체의 축·범례·색상·레이아웃 변경 | 실제 이미지/벡터가 달라지므로 승인 필요 |
| 데이터 plot 재실행·출판용 렌더·패널 재구성 | 자원 소모가 작아 보여도 승인 필요 |
| AI 이미지 생성·새 개념도 제작·이미지 교체 | 승인 필요 |
| 작은 재표현을 이유로 의미 있는 그림 삭제 | 자동으로 생략하지 않음; 사유와 대안을 제시 |

### 8.3 승인 요청의 구체적 내용

그림별로 다음을 보여준다.

- 어떤 reviewer 의견 또는 정합성 문제를 해결하려는지.
- 현재 그림과 문제 위치, 변경할 요소.
- 필요한 데이터·생성 파일과 수정된 스크립트/명세의 차이.
- 실행 방식, 출력 파일, 원본 보존 위치, 확인 가능한 자원·시간 예상. 근거가 없으면 “추정 불가”로 표시한다.
- 실행 후 본문·캡션·표·response에 함께 반영될 사항.
- `이 그림 수정 승인`, `현재 그림 유지`, `보류` 선택. 여러 그림을 명시적으로 선택해 함께 승인할 수 있다.

승인은 `sessionId + round + figureId + 입력 해시 + 수정 명세 해시 + 실행 방식`에 묶인다. 자료·명세가 바뀌면 승인은 무효이며 새 승인을 받는다. 승인 전에는 재생성 도구를 호출하지 않는다. 재시도가 추가로 자원을 소비할 수 있으므로 승인에 표시한 실행 횟수 범위 밖의 재생성도 다시 승인받는다.

승인 요청 중에도 독립적인 본문·표 작업은 진행한다. 해당 그림에 의존하는 변경과 “수정 완료” 답변은 보류한다. 회차 봉인 전에 승인된 결과를 검토에 포함하거나, 거절/보류 상태를 미해결로 명시한다. 단순히 시간이 지났다는 이유로 승인 처리하지 않는다.

재작성 결과는 새 파일로 저장하며 기존 이미지에 덮어쓰지 않는다. 결과의 캡션·본문·수치 대응을 검사한 뒤 패키지에 포함한다. 원자료 없는 실험 결과를 생성 이미지로 만들어서는 안 된다. 실행 도구가 준비되지 않았으면 구체적인 제작 요청서와 필요한 파일 목록을 남긴다.

## 9. 심사의견 입력과 답변서

### 9.1 실제 리뷰 입력

초기 버전은 reviewer별 붙여넣기와 TXT/Markdown 가져오기를 지원한다. 편집자 결정문은 별도 항목으로 입력한다. PDF/DOCX 첨부·추출은 후속 범위로 두되, 데이터 구조는 처음부터 원본 파일·페이지·주석 위치를 저장할 수 있게 한다.

원문은 수정하지 않고 보존한다. 구조화·번역·요약 결과는 원문과 나란히 둔다. 문장 분해 과정에서 빠진 요구, 중복 번호, 잘못 연결된 페이지를 사용자가 쉽게 고칠 수 있게 한다. 매칭이 확실하면 자동 진행하고, 의미가 달라질 수 있는 입력 오류만 확인 대상으로 표시한다.

### 9.2 의견 처리 결과

| 결과 | 의미 | 답변서 표현 원칙 |
|---|---|---|
| `changed` | 요구를 반영한 변경이 실제 적용됨 | 무엇을 어디서 어떻게 고쳤는지와 근거 |
| `clarified-no-change` | 원고에 이미 설명되어 있어 위치를 안내 | 변경했다고 쓰지 않음 |
| `reasoned-disagreement` | 근거를 들어 요청을 수용하지 않음 | 정중한 반박, 유지 이유, 가능한 보완 |
| `partially-addressed` | 일부만 반영됨 | 반영한 부분과 남은 부분을 구분 |
| `needs-author` | 핵심 판단이나 자료가 필요함 | 질문과 필요한 자료를 구체적으로 기록 |
| `awaiting-figure-approval` | 이미지 수정 승인이 필요함 | 완료로 처리하지 않음 |
| `unresolved` | 현재 범위에서 해결하지 못함 | 미해결 이유와 다음 행동 |

위 결과는 Claude의 대응 방식이다. GPT의 검증 상태는 별도 필드(`verified`, `not-verified`, `regressed`, `not-assessed`)로 보관한다. “Claude가 처리했다”와 “검증까지 통과했다”를 혼동하지 않는다.

### 9.3 답변 생성 순서

1. Claude가 통합 수정안과 대응 근거를 만든다.
2. 앱이 candidate에 패치를 적용하고 실제 변경 목록을 확정한다.
3. Claude가 확정된 변경·보류·반박에 근거해 답변을 쓴다. 적용 실패한 제안을 이미 수행했다고 쓰지 않는다.
4. 앱이 각 `changed` 답변의 연결된 패치·근거 위치를 검사한다.
5. GPT가 코멘트, 답변, 수정본, 원본 대비 차이를 함께 읽는다.
6. 2차 답변은 1차·2차의 변경을 합쳐 **최초 baseline 대비 누적 답변서**로 갱신한다. 1차에 처리된 사항을 빠뜨리지 않는다.

### 9.4 답변서 구성

```text
Response to the Editor and Reviewers
  Overall revision summary
  Editor comments
    E-C01: 원문 → 답변 → 수정 위치 → 필요시 수정 문구
  Reviewer 1
    R1-C01: 원문 → 답변 → 수정 위치 → 필요시 수정 문구
  Reviewer 2 ...
```

원고 수정은 원고 언어를, 공식 response는 설정된 제출 언어를 따른다. 저자용 설명은 UI 언어로 제공할 수 있다. 가상 모드 결과에는 가상 심사라는 표시를 유지한다. 실제 심사 모드의 공식 답변에는 내부 GPT QA 코멘트·프롬프트·작업 로그를 포함하지 않는다.

페이지·행 번호는 최종 렌더 파일이 있을 때 그 결과에서 얻는다. 편집 단계에는 절 제목·block ID·표/그림 ID·인용구로 위치를 기록한다. 페이지 매핑 기능이 없거나 확실하지 않으면 절·문구로 위치를 제공하고 번호를 추측하지 않는다.

내보내기 후 수동 편집이나 렌더 변경이 있으면 위치 정보를 stale로 표시하고 재계산한다. 미해결 항목은 저자용 보고서에 전부 표시하며, 실제 답변서에서도 원문 의견을 누락하지 않고 현재 대응을 사실대로 표현한다. 제출 사이트나 이메일로 자동 전송하지 않는다.

## 10. 사용자 화면과 작업 흐름

### 10.1 진입과 시작 화면

문서/프로젝트 메뉴에 `Review & Revision`을 추가하고 `가상 심사`와 `실제 심사 대응`을 선택하게 한다. 기존 Comments·Revision History는 일상 편집 용도로 유지한다.

시작 화면에는 기본값을 채워 둔다.

| 항목 | 기본값 또는 동작 |
|---|---|
| 원고 범위 | 현재 문서 + 연결된 표·그림·참고문헌; 관련 문서 추가 가능 |
| 실제 심사 baseline | 실제 제출본 선택을 안내; 현재본 사용 시 차이 기록 |
| 모델 | GPT reviewer, Claude reviser; 현재 연결 상태와 선택 모델 표시 |
| 반복 횟수 | 최대 2회, 1회 선택 가능 |
| 가상 reviewer | 분야·기여도 / 방법·통계 / 논리·보고 완결성 |
| 수정 강도 | 문제 해결에 필요한 최소 통합 수정 |
| response 언어 | 원고/제출 언어에서 제안 |
| 그림 | 재작성 전 승인 필수, 기본 해제 불가 |
| 저장 위치 | 원본 보관 위치와 별도 작업본 위치를 명확히 표시 |

시작은 전체 본문·표 자동 수정을 **별도 작업본에서** 수행하는 권한을 의미한다. 매 단계마다 동일한 허락을 다시 묻지 않는다. 데이터 부족, 양립 불가능한 연구 판단, 그림 승인만 필요 시 사용자 입력을 요청한다.

### 10.2 진행 화면

- 상단: 모드, baseline 날짜, 현재 단계, `1/2` 회차, 읽은 범위, 사용 모델.
- 왼쪽: 편집자/Reviewer 1..N과 의견 상태. 중복·충돌·승인 대기 필터.
- 중앙: 원본 대비 수정본, 블록별 변경과 표 셀 비교, 그림 미리보기.
- 오른쪽: 선택 의견의 원문, 대응 이유, 실제 변경, response, GPT 판정.
- 하단 또는 별도 탭: 통합 수정계획, 전체 일관성 보고서, 사용자 판단 목록.

`원본`, `작업본`, `1차 결과`, `최종 후보`를 경로와 라벨로 식별한다. 색만으로 구분하지 않는다. 진행률은 실제 완료된 절·자료·단계 기준으로 표현하며 근거 없는 예상 완료 시간을 표시하지 않는다.

### 10.3 완료·수동 수정

완료 화면은 “초기 18개 의견 중 12개 반영, 3개 반박, 1개 부분 반영, 2개 판단 필요”처럼 처리 결과를 보여준다. 이는 예시이며 실제 수치는 검증된 ledger에서 계산한다.

사용자는 최종 후보와 response를 함께 검토하고, 새 작업 사본에서 편집하거나 패키지를 내보낸다. 변경 묶음은 하나의 의견이 여러 절·표를 건드리는 단위로 보여주며, 부분 거절 시 관련 답변과 검증 결과를 무효화한다. 일반 editor에서 수정할 때도 연결된 결과를 stale로 표시한다.

최종 검토 이후의 수동 변경은 봉인된 결과를 덮어쓰지 않고 `manual revision` 사본을 만든다. 무결성 재검사는 가능하되 자동 Claude 수정은 상한을 초과해 시작하지 않는다. 새로운 실질 수정 cycle은 후속 세션으로 기록한다.

## 11. 데이터 모델과 실행 엔진

### 11.1 주요 데이터 개체

다음은 신규 설계이며 기존 타입이 이미 제공한다는 의미는 아니다. 모든 저장 형식에는 `schemaVersion`을 둔다.

| 개체 | 핵심 필드 |
|---|---|
| `ReviewSession` | id, mode, sourceProject, baselineId, manuscriptSet, roles, maxCycles, allocatedCycles, completedCycles, stage, status, selectedFinalRound, parentSessionId |
| `WorkspaceScope` | sessionId, workspaceId, readRoots, writeRoot, referenceScope, memoryScope, immutable |
| `SnapshotManifest` | 파일별 원래 위치·사본 위치·해시·크기·종류, 전체 packageHash, 누락 사유 |
| `ReviewerProfile` | reviewerId, human/virtual/editor, 표시명, 관점, 평가 기준, 원문 출처 |
| `ReviewComment` | id, reviewerId, parentId, 원문, 원문 위치, 요약, targetRefs, category, severity, sourceRound |
| `IssueRelation` | commentIds, duplicate/conflict/dependency, 관련 주장·자료, 조정 결과 |
| `RevisionPlan` | baselineHash, 유지할 원칙, 작업 목록, 영향 범위, 근거, 보류·반박 결정 |
| `PatchOperation` | operationId, 대상 파일·블록·셀, expectedHash, before/after, evidenceRefs, commentIds |
| `ResponseItem` | commentId, 대응 결과, 답변 전문, 변경 ID, 위치, 근거, unresolvedReason, GPT 검증 상태 |
| `FigureChangeRequest` | figureId, 입력·명세 해시, 실행 방법, 예상 자원, 허용 횟수, approvalId, 출력 해시 |
| `ValidationReport` | 검사명, deterministic/model, pass/fail/unknown, 근거 위치, 검토 범위, 심각도 |
| `RoundResult` | cycleNo, 입력 해시, 계획·변경·원고·답변·검사 파일, 완성 여부, GPT 판정 |
| `RunEvent` | eventId, jobId, 단계, attempt, 시작/완료 시각, model 정보, 입력·출력 해시, 오류 |

ID는 경로·제목·페이지 번호 변경에 흔들리지 않아야 한다. 모든 대상 참조는 `workspaceId + documentId + blockId`를 기본으로 하며 표의 행/열 ID와 그림 ID를 확장한다. 새 블록과 분리·병합된 표에는 이전 대상과의 대응 정보를 둔다.

### 11.2 상태 전이

```text
created → preflight → snapshotting → context-building → review-ready
  virtual: initial-reviewing
  peer:    importing-comments
  → planning(1) → revising(1) → applying(1) → responding(1)
  → validating(1) → gpt-assessing(1)
      → finalizing
      또는
      → planning(2) → revising(2) → applying(2) → responding(2)
      → validating(2) → gpt-assessing(2) → finalizing
  → completed 또는 completed-with-open-issues
```

실행 상태와 품질 상태를 분리한다. `completed`는 허용된 실행이 끝났다는 의미이며 `ready-for-author-review`, `needs-author-action`, `incomplete-coverage`, `invalid-candidate` 같은 품질 판정과 함께 표시한다. 사용자 검토가 남은 상태를 저널 제출 완료로 표시하지 않는다.

새 실질 수정 회차를 시작할 때 먼저 슬롯을 영속적으로 예약하고 `allocatedCycles`를 증가시킨다. 실패·취소로 슬롯을 자동 반환하지 않는다. 같은 회차 재개는 기존 슬롯을 사용하며 기술적 재시도 한도를 따른다. `completedCycles`만 세어 실패한 수정이 상한 밖에서 계속 반복되는 구현을 피한다. 두 번째 candidate까지 모두 유효하지 않으면 마지막 유효 패키지 또는 baseline과 미완료 보고서를 보존한다.

일시 중단 사유는 별도 필드로 기록한다: 사용자 일시정지, 인증 필요, 구독 한도, 그림 승인, 자료·판단 필요, 외부 변경 충돌. `failed`와 `cancelled`도 구별한다. 기술 오류를 “의견 없음”으로 처리하지 않는다.

### 11.3 영속화·원자성·복구

초기 구현은 세션별 JSON manifest와 append-only journal로 충분하다. 새 데이터베이스를 필수로 도입하지 않고 현재 파일 기반 저장과 일관되게 시작한다. 다만 기존 메모리 기반 `ProjectJobs`를 영속 실행 원장으로 간주하지 않는다.

1. 작업 시작 전에 입력 해시와 idempotency key를 기록한다. 키에는 세션·회차·단계·입력 해시·프롬프트 버전이 포함된다.
2. 모델의 스트리밍 출력은 임시 파일에만 기록한다. 정상 종료·파싱·검증 후 완성 결과로 확정한다.
3. 변경안은 별도 candidate 묶음에 적용한다. 여러 문서·표·그림·서지를 검증하고 저장이 끝난 뒤 한 개의 manifest 포인터를 원자적으로 갱신한다.
4. 검사 실패 시 부분 결과를 현재 작업본으로 노출하지 않는다. 실패 candidate는 진단용으로 보존하고 이전 정상 포인터를 유지한다.
5. 원고·답변·GPT 평가를 묶어 회차를 봉인한다. 검사 실패를 해결하는 새로운 학술적 수정은 다음 회차로 넘어간다. 단순 적용 실패는 같은 패치의 안전한 재적용만 허용한다.
6. 앱 종료 시 마지막 완료 단계를 저장한다. 재시작하면 완료된 결과를 재사용하고 중단된 단계에서 재개할 수 있다. 원격 호출이 끝났는지 불명확하면 완료 처리하지 않고 재호출 가능성을 안내한다.
7. 로컬 적용은 한 번만 반영되도록 보장한다. 외부 모델 호출의 exactly-once를 보장한다고 주장하지 않는다.
8. 세션당 writer는 하나만 둔다. 같은 앱의 중복 클릭과 여러 앱 프로세스의 동시 실행을 잠금으로 막고, 죽은 프로세스의 잠금은 검증 후 복구한다.
9. 사용자가 실행 중 작업본을 편집하면 기준 해시가 달라져 적용을 중지한다. 작성 중에는 읽기 중심으로 보여주고, 수동 수정은 일시정지 후 수행하도록 안내한다.
10. 일시정지·취소 후 늦게 도착한 모델 결과는 job ID와 stage token으로 무효화한다. 원본·완료된 회차·취소된 작업 기록은 보존한다.

그림 승인 대기는 해당 candidate에 연결된다. 이미 봉인된 회차를 나중 승인으로 덮어쓰지 않는다. 보류를 선택해 회차를 종료했다면 남은 허용 회차에서 처리하거나, 상한 소진 시 후속 세션으로 넘긴다.

### 11.4 호출량과 자원 관리

- 역할 수행은 기본 순차 실행한다. 현재 구독 클라이언트의 동시 실행 제약과 한도를 확인하기 전 무제한 reviewer 병렬화를 도입하지 않는다.
- 시작 전 문서 길이·표 수·그림 수·reviewer 수에 따른 예상 단계와 이미지 배치를 보여준다. 논리적 cycle과 실제 호출 횟수를 구분한다.
- 응답 시간 제한·전체 실행 예산·재시도 횟수는 설정 가능한 상한을 둔다. 실제 기본값은 장문·다중 그림 fixture와 연결된 모델로 측정해 결정한다.
- 같고 완전한 입력 해시의 완료 단계만 재사용한다. 모델·프롬프트·그림·기준표가 바뀌면 관련 cache를 무효화한다.
- 한도 도달 시 이미 만든 결과를 저장하고 다음 사용자 재개를 기다린다. 자동 유료 전환이나 승인 없는 그림 재실행은 하지 않는다.
- 완전한 모델 출력과 원문은 세션 안에 보존하고, 화면용 축약본은 별도로 만든다. 기존 revision log의 길이 제한을 적용하지 않는다.

## 13. 최종 산출물과 품질 판정

최종 패키지는 한 회차의 원고·답변·자료·검증 결과를 기준으로 만든다. manifest에는 각 파일 해시와 `selectedFinalRound`를 기록한다.

필수 산출물:

1. 편집 가능한 ScholarPen 원고와 그 원고의 표·그림·참고문헌.
2. reviewer별 response Markdown과 구조화된 response JSON.
3. baseline 대비 본문·표·그림·서지 변경표.
4. 미해결 의견·반박·저자 판단·그림 승인 대기 목록.
5. 전체 읽기 범위, 규칙 검사, GPT 평가를 구분한 품질 보고서.
6. 원문 의견, 회차별 이력, 승인 기록에 접근할 수 있는 세션 저장본.

선택 산출물은 QMD/DOCX/PDF이다. 현재 설치된 export·render 기능의 실제 지원 범위와 필요한 프로그램을 preflight에서 확인한다. 파일 확장자만 만든 뒤 내보내기에 성공했다고 표시하지 않는다. 외부 공유 묶음은 원고·답변·필요 자료만 포함하고, 내부 프롬프트·작업 로그·사용자 판단 기록은 기본 제외한다.

`ready-for-author-review` 조건은 다음을 모두 만족하는 것이다.

- 선택한 원고·표·그림에 대한 필수 검토 범위가 채워짐.
- 구조 검사를 통과하고 원본/작업본 참조가 섞이지 않음.
- 모든 원문 코멘트에 대응 결과가 있음. 대응 결과는 정당한 반박일 수도 있음.
- 변경했다고 쓴 답변이 실제 반영된 변경과 연결됨.
- 미해결 중대 모순이나 필수 그림 승인 대기가 없음.

이를 만족하지 못해도 안전하게 보존한 최종 후보와 결과 보고서는 제공한다. 단, `needs-author-action` 또는 `incomplete-coverage` 상태를 명확히 유지한다. 단일 AI 점수나 “accept” 판정만으로 위 조건을 대체하지 않는다.

## 14. 검증 계획과 수용 기준

계획서만 작성하는 현재 작업에서 아래 테스트를 실행했다는 의미는 아니다. 구현 완료를 판단하기 위한 요구사항이다.

| 검증 영역 | 시나리오 | 통과 기준 |
|---|---|---|
| 원본 보호 | 원본을 연 상태에서 리뷰·취소·재시작·내보내기 | 원본 원고·그림·서지 파일 해시가 전부 동일 |
| 저장되지 않은 내용 | 편집 직후 세션 시작, 협업 저장 지연 | 실제 최신 본문이 snapshot에 포함되고 혼합 버전 없음 |
| 기존 변경 제안 | 수락/거절 전 제안이 있는 원고 | 임의 수락 없이 기준본 확정 절차 수행 |
| 경로 격리 | 상대경로 탈출, symlink, 같은 파일명, 원본/작업본 동시 열기 | 허용된 workspace 밖 쓰기·우회 참조 차단 |
| 데이터 격리 | 원본·1차·2차에 동일 block/figure ID 존재 | 문맥·인덱스·협업·메모리가 해당 scope만 사용 |
| 상한 | V1/V2가 계속 추가 수정을 요구 | Claude 실질 수정 최대 2회, V2 후 자동 수정 0회 |
| 조기 종료 | 1차 검증에서 수정 필요 없음 | 2차를 호출하지 않고 동일한 원고/답변 묶음 확정 |
| 다수 reviewer | 상반된 인과 주장, 중복 요청, 충돌 문체 | 충돌 결정 기록, 동일 수정 1회, reviewer별 답변 유지 |
| 실제 리뷰 | 원문에 여러 하위 질문, 편집자 코멘트, 2,000자 초과 의견 | 원문 무손실, 모든 하위 요구 추적, 내부 GPT 의견과 분리 |
| 표 수치 | 분모 차이, 반올림, 결측, 잘못된 합계, 근거 없는 수치 | 근거 있는 계산만 수정; 불확실한 값 추측 없음 |
| 표 구조 | 행·열 이동, 병합 셀, 주석, 표 분할 | 데이터·캡션·참조 유지, 저장 후 동일한 의미로 재열림 |
| 그림 검토 | 4개 초과 그림, 큰 파일, 다중 패널, 누락 파일 | 배치별 검토 범위 기록; 미검토 그림을 검토했다고 표시 안 함 |
| 그림 승인 | 미승인·거절·보류·이전 입력 해시 승인·중복 클릭 | 미승인 재생성 0회, 유효 승인당 허용된 실행 횟수 준수 |
| 답변 정확성 | 패치 실패, 일부 거절, 변경 없는 반박 | 수행하지 않은 변경 주장 0건, 상태와 실제 원고 일치 |
| 누적 답변 | 1차에서 해결된 내용과 2차 추가 수정 | 최초 baseline 대비 전체 답변 유지 |
| 전체 흐름 | Results 변경이 Abstract·Conclusion과 충돌 | 연결된 절을 발견하고 수정 또는 명시적 미해결 처리 |
| 길이·범위 | 긴 원고 중간 절에 핵심 오류, 여러 파일 | 조용한 절단 없음; 전체 범위 검사 또는 불완전 표시 |
| 실패·복구 | provider timeout, 잘린 JSON, 파일 저장 실패, 앱 강제 종료 | 원본 보존, 부분 결과 비승격, 완료 단계 중복 적용 없음 |
| 외부 변경 | 실행 중 사용자가 작업본 수정 | 기준 해시 충돌 검출, 자동 덮어쓰기 없음 |
| 구독 경로 | GPT/Claude 인증·한도 오류, 이미지 미지원 모델 | 정확한 단계에서 중지, API/다른 모델 fallback 없음 |
| 최종 패키지 | 다른 위치로 폴더 복사 후 재열기·렌더 | 그림·표·서지 연결 유지, 페이지 위치는 실제 산출물과 일치 |
| 원고 형식 | citation, math, footnote, cross-reference, 중첩 블록 | 의도한 변경 외 구조·내용 보존 |
| 입력 오염 | 리뷰 원문에 파일 쓰기·추가 실행 지시 삽입 | 원문은 데이터로만 처리, 경로/도구/회차 정책 변경 없음 |

검증 순서는 작은 synthetic fixture → provider mock 통합 → 실제 구독 연결의 작은 원고 → 패키징된 macOS 앱 순서로 진행한다. 실제 계정과 앱에서는 두 provider 호출, 연결 그림 전달, 승인 대기, 중단·재개, 재열기, 독립 export까지 확인한다. build 성공이나 source test 성공을 설치 앱 검증과 혼동하지 않는다.

기본 회귀 검사에는 관련 Bun 테스트, TypeScript 검사, frontend build를 포함한다. 저장·편집·협업·export 접점을 변경한 단계에서는 해당 기존 회귀 테스트도 실행한다. 모든 단계에서 전체 suite를 반복하기보다 변경 위험에 맞춰 검증 범위를 넓힌다.

## 15. 구현 순서와 출시 범위

| 단계 | 구현 내용 | 완료 조건 |
|---|---|---|
| 0. 계약·검증 자료 | 세션 타입, cycle 정의, 충돌·표·그림 포함 fixture, provider capability 확인 | 두 모드의 성공/실패 경로를 재현할 자료와 계약 확정 |
| 1. 격리 저장 | snapshot, 독립 workspace, Y.Doc/서지/참조/메모리 scope, 잠금·journal | 원본 불변·재시작 복구·경로 격리 테스트 통과 |
| 2. 공통 수정 파이프라인 | 의견 ledger, 기준표·통합 계획, Claude 패치·답변, 실제 변경 검증 | 작은 다중 의견 원고를 일관된 새 패키지로 저장 |
| 3. 두 모드와 두 회차 | GPT 초기 심사/재검토, 실제 의견 import, 조기 종료·상한 | 가상/실제 모드 모두 최대 2회 end-to-end 통과 |
| 4. 표·그림 정합성 | 표 구조·수치 패치, 실제 이미지 검토, 그림 승인·새 파일 연결 | 본문과 자료의 불일치 검출·안전 수정·승인 차단 검증 |
| 5. 사용자 검토·출력 | 비교 화면, reviewer별 response, 수동 수정 무효화, export | 결과를 재열고 수정·비교·공유할 수 있는 완전한 흐름 |
| 6. 안정화 | 긴 원고, 복구·한도·동시 편집, 실제 provider/패키지 smoke test | 위 수용 기준의 핵심 항목 및 macOS 실제 흐름 통과 |

단계 2~3의 내부 시제품은 텍스트 중심으로 만들 수 있다. 그러나 사용자에게 요청한 기능이 완성되었다고 제공하는 첫 출시에는 **가상/실제 모드, 두 회차 상한, 원본 격리, 표 자동 수정, 실제 그림 검토, 재작성 승인, 답변 근거 연결**이 모두 포함되어야 한다.

처음부터 포함할 범위:

- 다수 reviewer, 편집자 의견, 심사의견 원문과 답변 보존.
- 한 논문을 이루는 선택된 여러 문서와 자료의 일관성 검사.
- 표 구조·표시 정리와 근거가 확정된 계산·수치 교정.
- 그림 검토와 승인 요청, 승인된 새 파일을 작업본에 연결하는 경로.
- 중단·재개·한도 오류·버전 충돌·기본 내보내기.

후속 확장:

- PDF/DOCX 심사의견의 자동 추출, PDF 주석과 tracked changes 가져오기.
- 저널별 응답 형식과 reviewer profile 템플릿.
- 여러 종류의 그림 생성·통계 렌더 도구를 연결하는 실행 adapter. 초기에는 검증된 한 경로 또는 사용자가 만든 대체 그림 파일 수령 경로를 지원한다.
- 제출 시스템 연동, 공동저자 승인, 대규모 raw data 재분석. 이는 이번 기본 자동 수정의 범위에 넣지 않는다.

실행 가능한 그림 재작성 도구가 없는 초기 출시에서는 “그림을 자동으로 다시 그린다”고 표시하지 않는다. 승인 요청서, 제작 명세, 대체 파일 가져오기, 반영 후 검증을 제공하고 자동 생성 경로는 실제 도구가 검증된 뒤 활성화한다.

일정은 저장 경계·Y.Doc 분리와 실제 이미지 전달을 단계 0~1에서 검증한 후 산정한다. 특히 기존 경로 전제가 넓게 퍼져 있으므로 단순 프롬프트 추가 수준의 작업으로 추정하지 않는다.

## 16. 주요 위험과 결정된 대응

| 위험 | 대응 |
|---|---|
| reviewer마다 고쳐 핵심 주장이 변함 | 기준표·통합 계획·영향 관계·전체 검토 |
| GPT와 Claude가 같은 오류에 동의 | 기계적 검사·원자료 증거를 별도 유지, AI 동의만으로 사실 확정 안 함 |
| 숫자를 맞추려 자료를 조작 | 데이터 출처·계산식 없으면 자동 수치 변경 금지 |
| 원본과 수정본이 메모리·참조로 섞임 | 저장 루트뿐 아니라 모든 문맥/인덱스/협업 scope 분리 |
| 반복 횟수와 자원 소비가 계속 증가 | 백엔드 2회 상한, 단계 예산, 제한된 기술 재시도 |
| 그림 승인 기다리다 전체 흐름 정체 | 독립 작업 진행, 의존 작업만 보류, 미해결 상태로도 안전한 결과 보존 |
| 원고는 고쳤는데 response가 이전 버전 | 해시 기반 무효화, 실제 적용 후 답변 생성, 패키지 단위 확정 |
| 가짜 “완료” 또는 검토 누락 | coverage와 unknown 상태, 완성과 제출 준비 상태 분리 |
| 파일이나 리뷰가 실행 지시를 포함 | untrusted 입력 취급, 모델에 직접 파일/쉘 권한 제공 안 함 |
| 저장 공간 증가 | 시작 전 공간 확인, 원본/완료 결과 자동 삭제 없음; 사용자 선택으로 세션 정리 |

원고와 리뷰는 선택한 외부 모델로 전송되는 자료다. 전송 범위를 시작 화면에서 표시하고, 접근 토큰을 세션이나 로그에 복사하지 않는다. 자료 삭제는 사용자가 해당 세션을 삭제할 때 수행하며 기존 원고까지 함께 지우지 않는다. cloud provider의 보존 정책을 앱이 임의로 보장하지 않는다.
